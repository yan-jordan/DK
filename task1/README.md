# موتور محاسبه‌ی هزینه‌ی ارسال «بازار» — تمرین ۱

پیاده‌سازی ۹ قاعده‌ی محاسبه‌ی هزینه‌ی ارسال برای مارکت‌پلیس فرضی «بازار». ورودی `orders.json` است و
خروجی `results.json` — یک رکورد به ازای هر سفارش، شامل هزینه‌ی هر مرسوله و مجموع کل.

---

## اجرا

پیش‌نیاز: **Python 3.9+**. هیچ وابستگی خارجی‌ای برای اجرای موتور لازم نیست (فقط کتابخانه‌ی استاندارد).

```bash
# از ریشه‌ی پروژه
python -m src.main
```

خروجی در `results.json` نوشته می‌شود و خلاصه‌ای در ترمینال چاپ می‌شود:

```
27 سفارش پردازش شد.
  ارسال رایگان : 9 سفارش
  مجموع هزینه‌ی ارسال : 1,355,000 تومان
  خروجی نوشته شد در : results.json
```

مسیر ورودی و خروجی قابل تغییر است:

```bash
python -m src.main --input data/orders.json --output data/results.json --quiet
```

```bash
pip install pytest
```

یک خط است و هیچ عدد جادویی‌ای در بدنه‌ی توابع تکرار نمی‌شود.

## منطق محاسبه در یک نگاه

```
برای هر سفارش:
    مرسوله‌ها = گروه‌بندی آیتم‌ها بر اساس seller_id          ← قاعده‌ی ۲

    اگر membership == "plus"  یا  مبلغ خالص ≥ ۵۰۰٬۰۰۰:      ← قواعد ۴ و ۵
        هزینه‌ی همه‌ی مرسوله‌ها = ۰  →  خروج

    برای هر مرسوله:
        اگر شامل آیتم حجیم است  →  ۱۵۰٬۰۰۰ ثابت              ← قاعده‌ی ۶
        وگرنه:
            وزن   = Σ (weight_grams × quantity)
            هزینه = ceil(max(0, وزن−۱۰۰۰)/۵۰۰) × ۵٬۰۰۰       ← قاعده‌ی ۳
            هزینه += پایه‌ی مقصد بر اساس city_tier            ← قاعده‌ی ۱
            اگر شبانه (به وقت تهران): هزینه × ۱٫۱             ← قاعده‌ی ۷
            هزینه += کارمزد پرداخت در محل                     ← قاعده‌ی ۸

    مجموع = min(Σ هزینه‌ی مرسوله‌ها, ۲۰۰٬۰۰۰)                 ← قاعده‌ی ۹
```

**سلسله‌مراتب اولویت** (پرمناقشه‌ترین بخش — دلیل کامل در بند ۱ `DECISIONS.md`):

```
معافیت سطح سفارش  >  کالای حجیم  >  قواعد عادی  >  سقف
```

## فرض‌هایی که گذاشته‌ام

مواردی که سند تکلیفشان را روشن نکرده بود و بدون داشتن پاسخ، فرض گذاشتم و ادامه دادم:

1. **مقادیر ناشناخته‌ی `city_tier`/`payment_method`** باعث خطا نمی‌شوند، بلکه به محافظه‌کارانه‌ترین
   حالت سقوط می‌کنند (گران‌ترین پایه / کارمزد پرداخت در محل). دلیل: در پردازش دسته‌ای، توقف کل اجرا
   به‌خاطر یک رکورد بد بدترین رفتار است.
2. **زمانِ بدون آفست** (اگر روزی در داده ظاهر شود) از قبل به وقت تهران فرض می‌شود.
3. **آستانه‌ی ۵۰۰٬۰۰۰ شامل‌شونده است** (`≥`)، چون تفسیر به نفع مشتری در موارد مرزی مدافعه‌پذیرتر است.
4. **«بالای ۱ کیلوگرم» غیرشامل است** — دقیقاً ۱۰۰۰ گرم هنوز هزینه‌ی وزن نمی‌گیرد.
5. **ترتیب مرسوله‌ها در خروجی** = ترتیب اولین ظهور هر `seller_id` در `items`، تا خروجی قطعی و
   قابل diff گرفتن باشد.

## روش بررسی درستی نتیجه

سه لایه‌ی مستقل:

1. **تست واحد قواعد** (`test_rules.py`) — هر قاعده جدا، با تمرکز روی مرزها: دقیقاً ۱۰۰۰ گرم، دقیقاً
   ۲۳:۰۰، دقیقاً ۰۶:۰۰، دقیقاً ۵۰۰٬۰۰۰ تومان.
2. **تست تصمیم‌ها** (`test_decisions.py`) — یک تست به ازای هر بند `DECISIONS.md`. هر تست علاوه بر
   assert کردن رفتار انتخاب‌شده، **عدد گزینه‌ی ردشده را هم صریحاً assert می‌کند** تا اگر روزی کسی
   تصمیم را برگرداند، تست دقیقاً بگوید کدام تصمیم عوض شده.
3. **تست طلایی** (`test_golden.py`) — کل خروجی روی کل دیتاست قفل شده، به‌علاوه یک تست که بررسی می‌کند
   `results.json` موجود در ریپو با خروجی کد فعلی یکی است (جلوگیری از تحویل خروجیِ کهنه).

علاوه بر این، محاسبات ۲۷ سفارش به‌صورت دستی هم بازبینی شدند و اعداد شاهد در `DECISIONS.md`
(مثل `(50000+80000)×1.1=143000` برای ORD-1018) از همان بازبینی دستی آمده‌اند.

### تست‌ها

```

tests/test_decisions.py   ← ۳۲ مورد : یک تست به ازای هر بند DECISIONS.md
tests/test_golden.py      ← ۳ مورد  : رگرسیون کل دیتاست
```

نمونه — هر تست تصمیم، هم رفتار انتخابی و هم گزینه‌ی ردشده را ثبت می‌کند:

```python
def test_decision_11_weight_is_multiplied_by_quantity(real_results):
    """
    ORD-1005: ۳ عدد کالای ۷۰۰ گرمی → وزن مرسوله ۲۱۰۰ گرم، نه ۷۰۰ گرم.
      تصمیم ما : ۱۵٬۰۰۰ (وزن) + ۳۵٬۰۰۰ (پایه) = ۵۰٬۰۰۰
      گزینه‌ی رد‌شده (بدون ضرب در تعداد): ۰ + ۳۵٬۰۰۰ = ۳۵٬۰۰۰
    """
    assert real_results["ORD-1005"]["total_shipping_fee"] == 50_000
    assert real_results["ORD-1005"]["total_shipping_fee"] != 35_000
```

## بخش‌هایی که کامل نشده‌اند و علتش

- **بازتوزیع مقادیر `shipments` هنگام فعال‌شدن سقف** — عمداً انجام نشده. ساختار خروجی در PDF دقیق
  مشخص شده و افزودن فیلدی مثل `cap_discount` از آن خارج می‌شد. توضیح کامل در بند ۵ `DECISIONS.md`.
- **لاگ هشدار برای داده‌ی ناسازگار** — `ORD-1021` (تناقض نام شهر با `city_tier`) و مقادیر ناشناخته‌ی
  enum فعلاً خاموش پردازش می‌شوند. در یک سیستم واقعی باید هشدار تولید کنند؛ افزودن یک لایه‌ی لاگینگ
  برای این تمرین بیش از حد بود.
- **سقف روی وزن غیرحجیمِ قابل جذب در مرسوله‌ی مخلوط** — بردار سوءاستفاده‌ی شناسایی‌شده در بند ۱۳، اما
  رفعش نیازمند عددی از تیم بیزینس است که در دست نیست.

## استفاده از هوش مصنوعی

- از یک دستیار هوش مصنوعی برای **بازبینی انتقادی** استفاده کردم: خروجی و مستندم را دادم و خواستم
  سخت‌گیرانه ایراد بگیرد. این بازبینی سه مشکل واقعی را پیدا کرد که خودم ندیده بودم:
  (۱) اینکه `weight_grams` را در `quantity` ضرب نکرده بودم در حالی که `unit_price` را ضرب کرده بودم،
  (۲) سناریوی مرسوله‌ی مخلوط حجیم/غیرحجیم در `ORD-1010` که در سند اصلاً توضیح داده نشده بود، و
  (۳) اینکه `ORD-1013` با آفست `+00:00` عمداً برای سنجش منطقه‌ی زمانی طراحی شده بوده.
- تصمیم‌های اصلی (به‌ویژه تقدم پلاس بر قاعده‌ی حجیم در بند ۱) **تصمیم خودم** است؛ AI در نقش وکیل مدافعِ
  طرف مقابل استدلال‌های ضدش را آورد و من پس از بررسی، روی تصمیم ماندم و استدلالم را در برابر آن‌ها
  تقویت کردم. اعداد گزینه‌های جایگزین در جدول بند ۱ را هم برای همین محاسبه کردم.
- ساختار ماژول‌بندی و نگارش تست‌ها با کمک AI انجام شد و سپس خط‌به‌خط بازبینی و اجرا شد.
- **نگارش خودِ `README.md` و `DECISIONS.md`:** کد و تصمیم‌هایم را به AI دادم و از آن خواستم این دو
  فایل را در قالبی مرتب و خوانا (جدول‌بندی، ساختار بندها، نظم مستند) بنویسد. این کار **فقط برای
  سرعت** انجام شد: تمام ورودی‌ها، تحلیل‌ها و تصمیم‌های داخل این دو سند، تصمیم‌های خودم هستند و
  دستورشان را خودم به AI دادم — نقش AI اینجا صرفاً قالب‌بندی و نگارش بود، نه تصمیم‌گیری.
- هر خط از این کد و مستند را می‌توانم توضیح دهم.
